02 · ENVIRONMENT SETUP

환경 셋업

도구 두 개와 자격증명 하나. 아주 단순하지만 한 번도 안 해본 사람이 가장 막히는 단계입니다.

① 도구 설치

# AWS CLI
brew install awscli

# Terraform (HashiCorp 공식 tap 필요)
brew tap hashicorp/tap
brew install hashicorp/tap/terraform
⚠️

Terraform은 2023년 라이선스 변경(MPL → BSL)으로 Homebrew core에서 제거됨. brew install terraform은 실패함.

② IAM 사용자 + 자격증명

  1. AWS 콘솔 → IAM → Create user
  2. 이름: terraform-admin
  3. AdministratorAccess 부여 (학습용)
  4. Security credentials → Create access key
  5. 로컬: aws configure --profile learning
💡

Root 키 절대 금지. 별도 profile learning으로 다른 계정과 분리.

🎙️ 내레이션
먼저 Homebrew로 AWS CLI를 설치하고, 그다음 Terraform을 설치했습니다. 여기서 작은 함정 하나. Terraform은 2023년에 라이선스를 BSL로 변경하면서 Homebrew core 저장소에서 빠졌기 때문에, HashiCorp의 공식 tap을 추가한 뒤 설치해야 합니다. 다음은 자격증명. AWS 콘솔에서 IAM 사용자를 새로 만들고, 학습 목적이므로 AdministratorAccess를 부여한 다음 Access Key를 생성했습니다. 루트 계정의 키를 직접 사용하는 것은 결제 정보까지 노출시킬 위험이 있어 절대 금지입니다. 로컬에서는 aws configure 명령으로 learning이라는 별도 프로파일에 키를 저장해, 다른 AWS 계정과 충돌하지 않도록 분리했습니다.
03 · PROJECT STRUCTURE

Terraform 프로젝트 구조

처음엔 모듈 분리 없이 flat 구조로. 파일 위치 추적이 쉬워 학습에 유리합니다. 

# aws_infra/
.gitignore           state·캐시 git 제외
provider.tf          terraform + AWS provider 설정
variables.tf         입력 변수 (region, CIDR, NAT toggle 등)
vpc.tf               VPC/Subnet/IGW/RT 리소스
outputs.tf           apply 결과 출력값
example.tfvars       변수 값 예시 (git에 올림)
README.md            사용법

provider.tf 핵심

terraform {
  required_version = ">= 1.5.0"
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.0" }
  }
}

provider "aws" {
  region  = var.aws_region    # ap-northeast-2
  profile = var.aws_profile   # learning

  default_tags {
    tags = {
      Project     = var.project_name    # learning
      Environment = var.environment     # dev
      ManagedBy   = "Terraform"
    }
  }
}
💡

default_tags로 모든 리소스에 공통 태그 자동 부착. 비용 분석(Cost Explorer)과 "Terraform이 관리 안 하는 리소스" 식별에 결정적.

🎙️ 내레이션
프로젝트 구조는 처음이라 모듈로 분리하지 않고 한 폴더에 평탄하게 두었습니다. 학습 단계에서는 파일이 어디에 있는지 한눈에 보이는 게 더 중요하기 때문입니다. 핵심 파일은 일곱 개. .gitignore가 가장 먼저인데, 이걸 안 만들면 실수로 terraform.tfstate를 커밋해 비밀번호나 IAM 키를 그대로 git 히스토리에 올릴 위험이 있기 때문입니다. provider.tf에서는 Terraform 버전과 AWS provider 버전을 핀하고, AWS 리전과 프로파일을 지정합니다. 특히 default_tags 블록은 모든 리소스에 자동으로 Project, Environment, ManagedBy 태그를 붙여 줍니다. 나중에 AWS Cost Explorer에서 비용을 그룹핑하거나, Terraform이 관리하지 않는 리소스를 식별할 때 결정적인 역할을 합니다.
04 · VPC ARCHITECTURE

VPC 아키텍처

두 개의 가용 영역(AZ)에 걸쳐 public/private subnet을 각각 두는, 다중 AZ의 표준 패턴입니다. NAT는 비용 절약을 위해 기본 비활성.

왜 다중 AZ?

같은 region 안에서도 AZ 단위로 장애가 발생합니다. RDS Multi-AZ, EKS 노드그룹 등 많은 AWS 서비스가 다중 AZ를 요구해 처음부터 2개를 잡아둡니다.

Public vs Private 차이는?

AWS 개념이 아니라 라우팅 결과의 분류입니다. Public = RT에 IGW 경로가 있고 public IP가 부여됨. Private = IGW 경로 없음 → 외부에서 직접 접근 불가.

🎙️ 내레이션
VPC의 IP 대역은 10.0.0.0/16. 약 65,536개의 IP를 확보합니다. 그 안에 가용 영역 두 개를 사용하고, 각 영역에 public subnet과 private subnet을 하나씩 두어 총 네 개의 서브넷이 됩니다. Public과 Private의 차이는 AWS의 내장 개념이 아니라 라우팅 결과입니다. Public subnet은 라우팅 테이블에 0.0.0.0/0이 인터넷 게이트웨이를 가리키도록 설정되어 외부에서 접근 가능하고, Private subnet은 그 경로가 없어 외부에서 직접 접근할 수 없습니다. 다중 AZ로 시작하는 이유는 RDS와 EKS를 포함한 많은 AWS 매니지드 서비스가 다중 AZ 구성을 요구하기 때문입니다. 처음부터 두 AZ로 잡아두면 나중에 데이터베이스나 컨테이너를 올릴 때 추가 작업이 필요 없습니다.
05 · EXECUTION FLOW

실행 명령어 흐름

Terraform의 핵심 사이클은 init → plan → apply. 여기에 안전장치로 fmt, validate를 끼워 넣습니다.

명령어하는 일안전성
terraform init provider 다운로드, .terraform/ 캐시, lock 파일 생성 네트워크만 사용. AWS 변경 X
terraform fmt -check HCL 포맷 일관성 검증 읽기만
terraform validate 문법/참조 무결성 검증 (init 필요) AWS API 호출 안 함
terraform plan 실제 변경 미리보기 (+ 생성, − 삭제, ~ 변경) 읽기만. 변경 X
terraform apply plan 그대로 AWS에 적용. state 갱신 ⚠️ 실제 변경
🎙️ 내레이션
Terraform의 작업 사이클은 크게 다섯 단계입니다. 먼저 terraform init. AWS provider를 다운로드하고 작업 디렉토리를 준비합니다. 다음 fmt와 validate로 코드의 포맷과 문법, 참조 정합성을 검증합니다. 이 두 단계는 AWS API에 접근하지 않기 때문에 자격증명 문제와 무관하게 동작합니다. terraform plan은 현재 코드와 실제 AWS 상태를 비교해, 어떤 리소스가 새로 생성되고, 변경되고, 삭제될지를 미리 보여 줍니다. 이 단계까지는 어떠한 변경도 발생하지 않으므로 안심하고 반복 실행할 수 있습니다. terraform apply가 비로소 실제 변경을 일으킵니다. plan 결과를 다시 보여 준 다음 yes 입력을 받아 AWS에 리소스를 생성하고, terraform.tfstate에 최종 상태를 기록합니다. 마지막으로 terraform state list와 terraform output으로 결과를 검증합니다.

07 · DECISIONS & TRADE-OFFS

핵심 결정과 Trade-off

처음 구축할 때는 "왜 이렇게 했는지"가 코드 자체보다 더 중요합니다. 나중에 돌아왔을 때 같은 고민을 반복하지 않도록 결정의 근거를 기록합니다.

결정선택근거
State backend 로컬 파일 혼자 작업이라 S3+DynamoDB까지 필요 없음. .gitignore로 git 차단
환경 분리 단일 환경 (dev) 학습 단계. dev/staging/prod 분리는 모듈화 시점에
디렉토리 구조 flat 코드 양이 적을 땐 한 폴더가 더 읽기 쉬움
NAT Gateway 기본 비활성 월 ~$43 (Seoul) 비용. 인터넷이 필요한 워크로드 추가 시 토글
AZ 개수 2개 RDS Multi-AZ, EKS 등 다중 AZ가 요구사항
IAM 권한 AdministratorAccess 학습 한정. 운영 환경은 최소 권한으로 좁힐 것
📋

State 안전장치: terraform.tfstate는 RDS 비밀번호 같은 민감 정보가 평문으로 들어갈 수 있어 .gitignore를 가장 먼저 만들었습니다.

🎙️ 내레이션
인프라를 처음 구축할 때 가장 중요한 건 코드 자체보다도 왜 그렇게 했는지에 대한 기록입니다. 몇 가지 핵심 결정을 짚어 보면. 첫째, State backend는 로컬 파일로 두었습니다. 혼자 작업하기 때문에 S3와 DynamoDB로 구성된 원격 backend까지 갈 필요는 없고, .gitignore로 git에 올라가지 않도록 막았습니다. 둘째, 환경은 dev 하나로 단일화. 학습 단계에서는 dev, staging, prod로 분리하면 복잡도만 늘어납니다. 셋째, NAT Gateway는 기본 비활성. 서울 리전 기준으로 idle 상태에서도 한 달에 약 43달러가 청구되기 때문에, 인터넷이 필요한 워크로드를 추가하는 시점에 변수 하나로 토글하도록 만들어 두었습니다. 넷째, 다중 AZ. 처음부터 두 개의 가용 영역을 잡아 두지 않으면 나중에 데이터베이스나 컨테이너를 올릴 때 다시 작업해야 합니다.
